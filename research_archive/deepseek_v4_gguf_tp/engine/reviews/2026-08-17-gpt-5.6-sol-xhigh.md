## Findings

### F1 [FATAL] Route A’s claimed fused decode path does not exist

**Attacked text**

> “a dedicated `mul_mat_vec_q_moe_launch` path with gate/bias fusion”  
> “Remaining work: id-format/TP-offset plumbing and vLLM op integration.” (§4.4)

**Evidence**

- `llama.cpp-ds4-study/ggml/src/ggml-cuda/mmvq.cu:699-705` shows `mul_mat_vec_q_moe_launch` accepts weights, Q8_1 activations, IDs, and output—no fusion argument.
- The multi-token branch at `mmvq.cu:823-830` calls that unfused launcher.
- More decisively, DeepSeek-V4 uses clamped SwiGLU. `ggml-cuda.cu:4331-4365` explicitly says `SWIGLU_CLAMP` has no MMVQ epilogue and batches ≤8 remain unfused. The fused MMQ up/gate path is prefill-only (`src1->ne[2] > 8`).
- `mmid.cu` compaction belongs to the MMQ path (`mmq.cu:226-249`); MMVQ directly indexes IDs (`mmvq.cu:626`).

The real Route A decode sequence is separate IQ2_XXS up and gate operations, clamped activation, Q2_K down, and top-k weighting/reduction. The cited “existing fused operation” cannot be the M2a unit of measurement.

**Required change**

Redefine Route A around a complete vLLM `FusedMoEExperts` operation. M2a must time routing preparation, one shared activation quantization, both IQ2_XXS launches, clamp, Q2_K launch, top-k reduction, casts, and TP reduction. Remove “nearly free” and revise the 3–5 day estimate.

### F2 [MAJOR] Route A omits the mandatory BF16→Q8_1 activation pipeline

**Attacked text**

> “Remaining work: id-format/TP-offset plumbing and vLLM op integration.”  
> “activation dtype bf16” (§4.4–4.5)

**Evidence**

The pinned kernels do not consume BF16 activations:

- MMVQ asserts F32 input and output at `mmvq.cu:1070-1071`, allocates Q8_1 scratch at `:1130`, then invokes `quantize_row_q8_1_cuda` at `:1135`.
- MMQ has the same F32 contract at `mmq.cu:108-109` and calls `quantize_mmq_q8_1_cuda` at `:248`.
- Quantization computes max, sum, scale, rounds 32 values, and writes `block_q8_1` (`quantize.cu:6-47`).

A literal TP=4 decode wrapper would quantize 4096 BF16 inputs separately for up and gate, then six 512-wide routed activations for down: 11,264 values/layer, about 484K values over 43 layers, plus F32/BF16 conversions. Sharing the up/gate Q8_1 buffer saves one 4096-value pass, but that requires a new API. The existing functions also emit F32 while vLLM’s surrounding graph and all-reduce use BF16.

**Required change**

Specify who performs BF16→Q8_1, whether up/gate share the quantized buffer, how F32 outputs return to BF16, and where caller-owned scratch resides. Include quantization, casts, and output conversion in both the performance budget and class-B oracle.

### F3 [FATAL] Graph capture is asserted without a capture-safe ABI

**Attacked text**

> “Both routes must be graph-capturable.”  
> M2a’s gate is only “projection from fresh-trace mix + all measured kernel times.”

**Evidence**

- `mul_mat_vec_q_moe_launch` is `static` (`mmvq.cu:699`), so it is not an exported operation vLLM can call.
- Public MMVQ/MMQ entry points obtain `ctx.stream()` (`mmvq.cu:1076`, `mmq.cu:114`), rather than accepting PyTorch’s current capture stream.
- They allocate scratch through a separate ggml pool. On a miss, that pool calls `cudaMalloc` (`ggml-cuda.cu:399-456`) or `cuMemCreate` (`:513-558`), either of which can invalidate capture if first encountered during it.
- The pool retains memory outside vLLM’s workspace manager and can leave captured graphs holding pointers subsequently reused by other calls.
- The actual graph replay/eager comparison is deferred to M6, after route selection and loader work.

**Required change**

Add an M2a gate requiring a real `torch.ops` wrapper that accepts the current CUDA stream plus caller-owned output/Q8_1/compaction workspaces. Pre-grow every allocation, capture and replay M=1–4 on TP=4, test multiple graph sizes for pointer aliasing, and account for retained scratch before route selection.

### F4 [MAJOR] A linear fresh-trace projection cannot be the go/no-go gate

**Attacked text**

> “The 58-floor projection is computed from (a)+(b)+(c)+(d) — measured components only.”  
> “dense Q8_0 GEMM at prefill M≈256” (§5)

**Evidence**

The replacement changes the scheduling graph, not just isolated durations:

- DeepSeek-V4 launches attention input GEMMs concurrently through `execute_in_parallel` (`vllm/models/deepseek_v4/attention.py:583,645`) and runs part of attention in an eager break (`:474`).
- MoE completion controls the start of the hoisted TP all-reduce (`nvidia/model.py:922-945,1055`).
- Changing expert and dense kernels together changes stream overlap, wave occupancy, graph topology, and NCCL’s available SM/bandwidth window.
- The base stack’s own benchmark warns that carrying one M-regime’s throughput into another was wrong by up to 5.6× (`benchmarks/kernels/benchmark_dsv4_sm80.py:3150-3162`). A single M≈256 point therefore cannot project serving prefill.

**Required change**

Use linear projection only as a pessimistic screening bound. Before any kill or promotion, run a TP=4 graph-captured decoder-layer slice containing Q8 dense kernels, the full Route A expert operation, and the real all-reduce. For prefill, benchmark the M distribution observed in the fresh trace, not one nominal M.

### F5 [MAJOR] M2 requires a measured `wo_a` implementation scheduled for M4

**Attacked text**

> “M2 therefore requires … `wo_a` path time.”  
> M1 only scopes it, while M4 delivers “Q8_0 repack … + `wo_a` path.”

**Evidence**

The M2 projection promises all measured components, but no working grouped/diagonal Q8 `wo_a` path exists until M4. The plan itself rejects the existing fallback at 34.01 tok/s and says standard FP8 Marlin-diagonal does not apply. A design sketch or isolated ordinary Marlin GEMV cannot provide the required BMM-serving time.

The M2a kill logic is also incomplete:

> “both Route A projection < floor → escalate to M2b”

It defines no outcome when only decode or prefill misses. Route B changes expert kernels and cannot repair a miss caused by dense Q8 or `wo_a`.

**Required change**

Move a minimal Q8 repacker and real `wo_a` serving-shape prototype into M2. Replace the combined pivot with a causal matrix: expert-caused miss → Route B; dense/`wo_a` miss → dense redesign or stop; one-metric-only miss → explicit decision.

### F6 [MAJOR] The family-level TP residency rules are already contradicted by the base model

**Attacked text**

> “`token_embd`, router, indexer, compressor, HC … replicated families”  
> “experts/attention/vocab shard; indexer, compressor, HC, router replicate” (§3)

**Evidence**

These two plan statements contradict each other and the pinned vLLM model:

- Token embeddings use `VocabParallelEmbedding` (`nvidia/model.py:1113`), so `token_embd` is vocabulary-sharded.
- The merged `wq_a + wkv` projection explicitly uses `disable_tp=True` and is replicated (`attention.py:265-271`).
- `wq_b`, `wo_a`, and `wo_b` use different column/row sharding rules; “attention shards” is not a valid family rule.

This affects both loader correctness and the replicated-memory delta currently set to zero in the 140K point estimate.

**Required change**

Replace family-level rules with a tensor-level table: GGUF name and logical shape, destination parameter, fused-slot order, TP axis, rank slice, quant-block row axis, runtime dtype, and post-load storage. Derive capacity from that table.

### F7 [MAJOR] Byte checks cannot detect a logically transposed or mis-fused GGUF load

**Attacked text**

> “checksum fail-closed against the M1 inventory”  
> “checksums on every tensor view”  
> M4 gate: “byte-identity assert on packed IQ2_XXS/Q2_K views”

**Evidence**

The source layouts require coordinate-aware mapping:

- GGUF routed gate/up are `{K, N, E}`, while down is `{N, K, E}` (`src/models/deepseek4.cpp:157-159`).
- GGUF stores `wq_a` and `wkv` separately (`:133,135`), but vLLM stacks them into `attn.fused_wqa_wkv` in a fixed order (`nvidia/model.py:1269-1276`).
- Similar fused mappings exist for compressor weights.

A transpose, wrong expert/rank offset, or reversed fused-slot order can preserve the exact byte multiset and checksum. L0’s random dequantization oracle validates block decoding, not the artifact’s logical coordinate mapping.

**Required change**

Add an artifact-aware class-A2 oracle. For every tensor family and TP boundary, sample `(expert, output row, input column)` coordinates, derive the GGUF byte offset, decode independently, and compare the destination’s logical value. Include first/last block, first/last rank, fused-slot boundaries, and hash-table rows.

### F8 [MAJOR] The tokenizer audit targets the wrong vLLM path and then bypasses it

**Attacked text**

> “the WNA16 stack uses HF tokenizer.json + vLLM template”  
> “Class-B/D prompts are pinned to token IDs, not text.”

**Evidence**

The pinned stack does not use an ordinary Jinja template for DeepSeek-V4 chat rendering:

- Architecture resolution automatically selects `tokenizer_mode="deepseek_v4"` (`vllm/config/model.py:644-660`).
- That tokenizer overrides `apply_chat_template` and calls a custom `encode_messages` implementation (`vllm/tokenizers/deepseek_v4.py:25-60`) containing DSML, tool, thinking, and reasoning-effort behavior.

A GGUF bootstrap that fails to preserve the `DeepseekV4ForCausalLM` architecture selection silently falls back to generic HF mode. Meanwhile, token-ID-pinned probes cannot catch that failure because they bypass rendering and tokenization entirely. M1 lists a tokenizer diff but its gate does not require parity.

**Required change**

Define config/bootstrap before module and tokenizer construction, pin the tokenizer mode explicitly, and add text/API→token-ID golden tests for ordinary chat, high/max reasoning, tool calls, and post-tool continuation. Keep token-ID probes for kernel isolation, but not as tokenizer evidence.

### F9 [MAJOR] The DeepSWE gate is neither statistically specified nor costed

**Attacked text**

> “≥3 seeds or seed-fixed where the harness allows”  
> “decision pre-registered on the paired statistic (discordant tasks + mean-partial delta)”  
> M8 estimate: “2–4 d”

**Evidence**

- Three seeds imply at least `12 tasks × 2 engines × 3 seeds = 72` serial task cells—six full 12-task sweeps in the stated one-worker harness.
- If seed/task pairs are treated as 36 independent discordant observations, variance is understated because three runs of one task are clustered. If results are aggregated by task, the effective binary sample remains 12.
- “Discordant tasks + mean-partial delta” names two endpoints but gives no combination rule, alpha, confidence interval, non-inferiority margin, tie rule, or missing/failed-cell policy.
- “seed-fixed where the harness allows” permits a different replicate count by task, making the paired statistic undefined without weighting.
- No measured one-seed pilot duration supports the 2–4 day estimate.

**Required change**

Pre-register the unit of analysis and an executable rule—for example, task-cluster bootstrap or hierarchical permutation over task then seed, with a stated non-inferiority margin and an intersection/lexicographic rule for strict and partial reward. Run one paired-seed pilot, record wall time and failure rate, then price all 72 minimum cells.

## Verdict

**STOP** — Route A is not the fused operation described, its mandatory activation-quantization and capture-safe stream/workspace ABI are absent, and M2’s projection depends on an unimplemented `wo_a` path while ignoring TP=4 critical-path interactions. The capacity sensitivity itself is sound: the anchors yield 5.8319 KiB/token/rank and 17,559 tokens per 100 MiB; the exact artifact-delta calculation gives about 139,147 tokens before replicated/runtime deltas. That arithmetic does not rescue gates capable of selecting or killing the wrong route. Revise F1–F5 before approving M0/M2 execution.
