# Adversarial review: `.research/gguf-tp-engine/PLAN.md`

The plan’s objective (exact Antirez GGUF bytes in a TP runtime) is not the issue. The draft as written would measure the wrong GPU, keep a stack that does not exist on the pinned tree, treat a prefix-cache as extra active context, and call a format conversion “numerically identical.” Several success numbers are then derived from those errors.

---

## Findings

### F1 [FATAL] The 230K / 430K “offload tier” success line treats a prefix-cache as extra active context

**Plan text:** “Context on-GPU / with offload tier | ≥ 150K / 230K | 180K / 260K | 230K / 430K” and “Reaching 230K+: engage the 16 GiB KV-offload tier (measured performance-inert below ~275K tokens, already the serving default pattern).” Stretch 430K is the llama.cpp Q8_0-KV number.

**Contradiction:** The WNA16 compose itself says the 16 GiB tier “is not part of the measured 230K performance path.” The speed-stack HTML repeats that it is “a host eviction safety tier.” The 2026-08-15 TP=4 offload campaign **stopped without a 0/16/24 GiB request comparison** and recorded the actual contract:

> Native vLLM CPU offload restores reusable prefixes before computation. It does not make ordinary active decode attend directly to CPU-resident history. … Expect no benefit for unique prompts or continuously active decode. CPU offload is a reuse tier, not a larger active GPU attention window.

`275,238` is **GPU** KV tokens at `max_model_len=230144` (1,355 blocks), not host-extended active context. “Inert below ~275K” is “the unused 16 GiB reservation did not slow the all-on-GPU 230K path,” not “paging the missing ~80K tokens of a 150K-on-GPU GGUF run is free.”

If GGUF only holds ~150K on GPU, a 230K **unique** request must either stay on GPU or restore KV every step. GPU0 is PCIe Gen3 x4 at **3.05 GiB/s H2D** (measured in that same offload report); a synchronized TP=4 restore waits on that rank. llama.cpp’s 430,080 is Q8_0 KV with layer-split, not `fp8_ds_mla` plus host prefix-cache.

**Required change:** Split three numbers and gate them separately: (1) on-GPU unique-request context, (2) aggregate GPU KV including concurrency, (3) prefix-reuse hit rate if the 16 GiB tier is kept. Drop 230K/430K as offload-backed **active** decode success. If 230K unique context is mandatory, it must fit on GPU or a measured paging path has to beat a named ITL floor on GPU0’s 3 GiB/s link.

### F2 [FATAL] “Keep Marlin-wo_a” is an FP8-weight path; GGUF `wo_a` is Q8_0

**Plan text:** Keep list includes “Marlin-wo_a.” Risk register: “Marlin-wo_a + bounded-RoPE already in base.” Capacity: +0.5 GiB/rank is the only GGUF tax.

**Contradiction:** The 688 MiB recovery is specifically: keep **block-FP8** `wo_a` + scales, pack for **FP8 Marlin**, flatten grouped projections, take the diagonal (`VLLM_DSV4_WO_A_MARLIN_DIAGONAL=1`). Disabling the BF16 cache without that path cut decode from ~62 to **34.01 tok/s** at 230K — below this plan’s 58 floor.

Antirez’s recipe stores `attn_output_a` / `attn_output_b` as **Q8_0**, not block-FP8. There is no `weight_scale_inv`. The Ampere attention path that FlashMLA decode feeds still does inverse-RoPE + grouped `wo_a` (`is_bmm=True`). Generic compressed-tensors already broke that layout once on FP8 (“transformed grouped `wo_a` weights into a layout incompatible with the DeepSeek attention path”).

Three outcomes, none in the plan:

1. Cache BF16 `wo_a` again: **+688 MiB/rank**, which is larger than the entire +0.5 GiB GGUF tax and collapses on-GPU context far below 150K.
2. Dequant every token: historically **34 tok/s**.
3. New Q8 grouped-Marlin diagonal: unscoped work, not “keep.”

FlashMLA decode only requires `fp8_ds_mla` **KV**. It does not make Q8_0 `wo_a` run the FP8 Marlin diagonal kernel.

**Required change:** Put Q8_0 grouped `wo_a` on the critical path in M1/M4 with an explicit kernel choice and a VRAM delta. Do not list Marlin-wo_a as untouched. Add a kill: if the only working path is BF16 cache or per-token dequant, stop — that path already lost both capacity and the 58 floor.

### F4 [MAJOR] The 0.55 GiB/token/rank budget does not cause 13.3 ms/token, and it divides the wrong bytes

**Plan text:** “routed experts ≈ 72.56 GiB × 6/256 activated ≈ 1.70 GiB, + shared/attention Q8_0 ≈ 0.5 GiB, ÷ 4 ranks ≈ **0.55 GiB/token/rank**. At WNA16's measured kernel efficiency this demand produced 13.3 ms/token (74.98 tok/s).”

**Contradiction:**

- DwarfStar audit of this exact blob: routed experts **72.562500 GiB**; other **layer** tensors **6.686476 GiB**; remaining ~1.51 GiB is embed+head. Non-routed traffic per decode step is ~7.2 GiB total, not 0.5 GiB. 0.5 GiB is off by ~14× on that term.
- vLLM TP does **not** shard everything. Residency audit: experts and vocab shard; attention / compressor+indexer / HC / router are replicated (indexer 191 → 767 MiB/rank). `÷ 4` on “shared/attention” is false for those families.
- 0.55 GiB in 13.3 ms is **41 GB/s**, ~4% of 936 GB/s peak. That cannot be the causal decoder. Nsight on the pre-FlashMLA decode baseline (`nsight-baseline-6`): NCCL all-reduce **18.8%**, sparse decode **13.7%**, Marlin **~23%**, all Humming W2/W4 kernels **~14.7%**. Weight traffic is a minority; “same demand → 13.3 ms” does not follow.
- GGUF routed vs WNA16 routed is not uniformly “+6% in the same bpw class.” WNA16 uses mixed W2/W4 and groups 128/256/512; GGUF is IQ2_XXS codebook + Q2_K affine.

**Required change:** Replace the 0.55 GiB story with a per-family byte budget (sharded vs replicated) and the nsys fractions. Predict tok/s from **Humming time / Marlin time / FlashMLA time / AR time**, not from a single GB/token number. State the observation that would falsify the dominant term.

### F5 [MAJOR] The ≥60% M2/M3 gate is on the wrong GPU, and 75 tok/s stretch is not implied by 60%

**Plan text:** “A100 microbench at decode+prefill shapes”; “if the fused fragment … cannot reach ≥60% of the W2-WNA16 kernel's throughput after two tuning iterations, the 58-tok/s floor is at risk”; estimate band 55–75; stretch 75 = WNA16 parity.

**Contradiction:**

- A100 is SM80. Humming JIT emits arch-specific cubins. You cannot run `sm_86` cubins on A100, and SM80 cubins do not validate 3090 (100 KB smem, 82 SMs, no TMA). The 7-case oracle that **did** matter was on 3090. Renting A100 copies the **quantization** rental, not the kernel gate.
- Using the nsys mix: Humming is ~15% of kernel time at the ~62 tok/s baseline. After FlashMLA+AR (~13.3 ms), that is ~2.3 ms/token. At 60% of W2 Humming: ~3.9 ms, **~67 tok/s** if nothing else regresses — so 60% does not sit on the 58 knife-edge. At **40%** (MMVQ-like vs MMA): ~59 tok/s. At **30%**: ~53 tok/s. The gate needs a pinned W2 GB/s or µs number at the real serving shape, not “60% of an unnamed kernel on A100.”
- Stretch 75 tok/s requires GGUF codebook fragments ≈ W2 int-unpack MMA **and** Q8_0 Marlin ≈ FP8 Marlin **and** `wo_a` unchanged. The plan already says IQ2_XXS/Q2_K are “instruction-heavier.” 75 is not a stretch of 60%; it is a different hypothesis.
- Two tuning iterations is self-graded. The MMVQ campaign on these exact formats spent a full decode campaign and closed at ~+1.5% vs a 10% bar.

**Required change:** M2/M3 microbench and NCU on a 3090 (co-resident is how MMVQ was done). Pin the W2 baseline as a measured µs and GB/s at `M=1–8`, `K=4096/2048`, `R≤8` per expert. Map fragment throughput to e2e with the nsys mix before claiming 58/70/75. Put Q2_K (affine `dmin`, not Humming `IntegerType<2>`) on the same kill as IQ2_XXS. Require graph-capturability; an eager-fast fragment that breaks breakable CUDA graphs falls toward the 5.5 tok/s eager regime.

**Plan text:** “Prefill inherits the vLLM chunked-prefill stack with our fragments in the batch-shape regime MMQ already wins: estimate 700–950 tok/s.” Target 700, stretch 900.

**Required change:** Prefill estimate and stretch must be ≤ measured WNA16 887 unless a larger `max_num_batched_tokens` is shown to fit GGUF VRAM. Gate prefill at serving M≤256, not “MMQ already wins at large M.”

### F7 [MAJOR] Q8_0 → compressed-tensors int8 g32 is not “numerically identical”

**Plan text:** “Q8_0 is symmetric block-32 int8 — numerically identically expressible as compressed-tensors int8 group-32 (pure repack, zero quality change, existing W8A16/Marlin kernels).” Quant method: “dense = CT int8-g32, control = BF16.”

**Contradiction:**

- GGUF Q8_0 (`ggml-common.h`, `dequantize_row_q8_0`): `int8 qs[32]`, fp16 `d`, `y = qs[j] * float(d)`.
- CT WNA16 8-bit (`compressed_tensors_wNa16.py`): `scalar_types.uint8b128` (offset 128), packed int32, `weight_scale` in **`params_dtype`** (this model is bf16). Marlin then tile-packs.
- fp16 `d` → bf16 scale drops mantissa bits. uint8b128 plus Marlin layout is a conversion, not a view. L0 “bit-exact dequant vs llama.cpp” will **fail** on the Q8_0 path if the oracle is llama.cpp `dequantize_row_q8_0` and the runtime is Marlin.
- “Existing W8A16 kernels” are GPTQ-style Marlin, not GGUF Q8_0 vec_dot. Accumulation order and scale dtype differ by construction.

**Required change:** Call it a **lossy-in-the-last-bits repack**. Oracle: compare Marlin output to Q8_0 dequant+GEMM with a stated atol/rtol, not “zero quality change.” Keep scales in fp16/fp32 if Marlin allows. Do not put Q8_0 under L0 bit-exact.

### F8 [MAJOR] “Q8_0 elsewhere” / `gguf_dsv4` does not match the pinned artifact; fail-closed will fire or silently downcast

**Plan text:** “IQ2_XXS routed gate/up, Q2_K routed down, Q8_0 elsewhere”; “dense = CT int8-g32, control = BF16”; “If the tensor inventory doesn't match the pinned contract exactly, load fails.”

**Contradiction:** Antirez README for this file:

| Class | Actual type |
|---|---|
| routed gate/up | IQ2_XXS |
| routed down | Q2_K |
| shared experts, attn projections, `output.weight` | Q8_0 |
| `token_embd`, router, indexer, compressor, HC | **F16** |
| norms, sinks, bias | **F32** |

1,328 tensors. MTP is a **separate 3.6 GiB file**, not inside this blob. `control = BF16` would downcast F32 norms/sinks. Fail-closed exact-match against a contract that says “Q8_0 elsewhere” either rejects the real file or mis-routes F16/F32/I32.

**Required change:** M1 inventory is the contract, and it must list F16/F32/I32/Q8_0/IQ2_XXS/Q2_K by tensor class **before** CUDA. Quant method needs a third bucket (F16/F32 control), not BF16. Do not cite in-tree `gguf.py` as reusable on this pin. “Future RL-refreshed weights load day one” contradicts fail-closed exact inventory — drop it or define a compatibility window.

### F9 [MAJOR] The oracle ladder can pass and still lose quality or speed

**Plan text:** “any divergence is our bug”; L6 “parity required; divergence means an integration bug, never ‘quant noise,’ because the weights are identical.”

**Contradiction:** Even with byte-identical expert storage, the serving path is not llama.cpp:

| Path | llama.cpp canonical | planned vLLM |
|---|---|---|
| KV | Q8_0 K/V | `fp8_ds_mla` (584 B UE8M0 row) |
| Attention | fork sparse + `LLAMA_ATTN_ROT_DISABLE=1` | FlashMLA decode + Triton prefill |

| Graphs | capture-always prefill | breakable decode graphs |
| `wo_a` | Q8_0 matvec | FP8 Marlin diagonal or a new Q8 path |

L0–L3 never execute KV, FlashMLA, AR, or graphs. L4 “fp tolerance / KL bound” has no numbers — self-graded. L5 NIAH at 200K is unrunnable if M5 only fits ~150K on GPU (F1). DeepSWE 12-task noise is not specified; 6 vs 5 solves is not a clean “integration bug” detector.

WNA16 already showed a parser bug looking like “bad quant.” The inverse error: treating FlashMLA+fp8 KV numeric drift as a loader bug, or waving it through as “tolerance.”

**Required change:** Split oracles: (A) weight-dequant identity for IQ2_XXS/Q2_K only; (B) known-delta runtime (KV, attn, Q8 Marlin) with **pre-registered** KL/NIAH/DeepSWE windows vs llama.cpp; (C) graph replay vs eager determinism; (D) rank-order AR. Do not claim L6 can only fail from integration bugs. Put NIAH 200K after a real 200K **on-GPU** capacity, or cut it.

### F10 [MAJOR] On-GPU 150–160K arithmetic is optimistic and MTP recovery is likely zero

**Plan text:** “GGUF is +2.0 GiB total (+0.5 GiB/rank) → on-GPU KV pool ≈ 0.85 GiB → **~150–160K**.” “MTP audit (M1) may recover ~2 GiB if those tensors exist.”

MTP: official `num_nextn_predict_layers=1`, but Antirez ships MTP as a **separate 3.6 GiB** file. WNA16 already omitted MTP. There is nothing to drop from this GGUF.

**Required change:** Capacity from a residency table (registered / unregistered / graphs / KV / headroom), not file-size/4. Remove MTP as a lever for this blob. Set the on-GPU floor after M1 inventory + `wo_a` path (F2), not 150K as a given.

### F13 [MAJOR] A cheaper path to the same bytes is ignored: call the already-measured ggml-cuda kernels from vLLM TP

**Plan text:** Core work is “extend the Humming indexed-expert mainloop with two new weight-format fragments — IQ2_XXS and Q2_K dequant fused at the fragment-load stage, feeding the same mma pipeline.” DwarfStar CUDA-TP is correctly dead (24 GiB slab gate). No other alternative.

**Contradiction:** The expensive unknown is codebook-into-MMA at M=1–8. The encodings already have SM86 MMVQ/MMQ kernels, measured on this host (IQ2_XXS 346–358 GB/s, Q2_K ~307 GB/s, Q8_0 713 GB/s). TP sharding of GGUF blocks is alignment math (2048/4=512, block 256). Wrapping those kernels as vLLM ops keeps FlashMLA, hier AR, `fp8_ds_mla`, and the scheduler, and skips M2/M3 research. Nsys says Humming is only ~15% of decode kernel time; a slightly slower expert kernel can still clear 58 if the rest of the 74.98 stack is actually present (F3).

Fusing LUT+sign+Q2_K `dmin` into a CUTLASS-style MMA mainloop is the high-risk way to save a minority of step time.

**Required change:** Make “ggml-cuda expert ops in vLLM TP” M2, and Humming fused fragments a stretch if MMVQ-in-TP misses 58. That is the same objective with a smaller kernel surface.

## Verdict

**PROCEED-WITH-REVISIONS**

Do not start M0 on this draft. The goal (Antirez bytes, TP, 3090, llama.cpp stays canonical until a real quality gate) can still be right: nsys shows expert MMA is a minority of WNA16 decode, so a slower GGUF expert kernel can clear 58 **if** FlashMLA, hier AR, graphs, and a working `wo_a` path are actually on the branch. This text does not pin that branch, does not own Q8_0 `wo_a`, treats a prefix-cache as 230K active context, grades kernels on A100, calls a Marlin conversion bit-exact, and describes an artifact that is not “Q8_0 elsewhere.”

Rewrite, then M0: pin `b7766cfe`; inventory F16/F32/I32; specify the Q8 `wo_a` kernel and VRAM; drop offload-backed 230K/430K; put M2/M3 on a 3090 with a mapped e2e budget; keep CT experts until M7; consider ggml-cuda expert ops before Humming codebook MMA. Until those land, executing the plan as written is how you spend 6–9 weeks proving a stack you did not build.
